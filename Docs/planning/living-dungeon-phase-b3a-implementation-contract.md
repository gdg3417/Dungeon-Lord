## Authority and eligibility

The owner's B3A instruction authorizes controlled synthetic qualification only. The approved long-term automatic living-dungeon direction remains the owner design locks; B3A does not activate it. Production continues to create a dormant schema-15 owner, manual runs retain their established behavior, and B2 advancement retains terminal checkpoints unconsumed.

The entire qualification scope and settlement entry point are `UNITY_EDITOR` only, internal to the existing detached authority. They are absent from player builds and have no GameRoot, SaveService, UI, wall-clock or application-foreground adapter. There is no `isForeground` parameter. This deliberately narrower boundary avoids introducing a production assertion API or persistent authorization owner.

A scope starts with exact validated complete-save bytes. It does **not** qualify any preexisting party. Only admissions performed by its controlled `Advance` calls become qualified, and every subsequent committed event must occur through the same scope. The existing authoritative scheduler creates the complete start and event-prefix checkpoint. The scope tracks each qualified party's current complete checkpoint identity and the exact complete-save predecessor bytes after each successful transaction. That checkpoint pins the party/start, ordinal, accepted deadline, complete committed event/consequence digest and terminal metadata. Thus qualification covers admission through terminal; it is never added to a terminal snapshot afterward. Tracking remains bounded to retained parties.

Other reviewed canonical edits/manual runs may be executed through the scope; they advance its exact predecessor binding without adding provenance for existing parties. An unobserved write makes the scope stale. Reopen with identical bytes can continue a still-live scope; a new scope after process restart cannot recreate the authorization. No evidence reconstruction/import is supported. Failed proven rollback retains the previous scope and can retry. Recovery-required uncertainty blocks that scope permanently.

`Prepare` first selects the earliest terminal party, then checks its qualification. It issues an in-memory request nonce bound to that exact scope, party/checkpoint and predecessor. A fabricated request, another scope's request, changed checkpoint/revision/session, or consumed request cannot authorize anything. Success invalidates the nonce; repeating it cannot settle the next party. Fresh authorization is required for each separate settlement.

## Selection and transaction

Only a fully validated, activated, closed scheduler boundary is eligible. Complete-save parsing independently validates the supported injected profile, storage/replay bounds, allocator and party pins. Selection reconstructs terminal parties and verifies RunId, timing, unconsumed terminal state, last committed Terminal kind, `last.Ordinal + 1 == NextOrdinal` using checked arithmetic, and terminal logical time. Order is checked `AdmittedAt + terminal.LogicalTime`, numeric RunSequence, then terminal event ordinal. Enumeration order is irrelevant. RunSequence uniqueness makes the third tie-break unreachable between distinct valid records, but it is explicitly retained in the comparison. An ineligible earliest party blocks the operation.

The writer checks persisted predecessor bytes, repeats validation/selection/authorization, restores the selected actual B1 executable and consumes its outcome only on the detached candidate. It neither advances other parties nor starts another simulation/RunId. The single settlement removes precisely that record and increments the Living Dungeon semantic revision **once** by checked addition. It does not change scheduler fields or other party/checkpoint bytes. Rejection, duplicate, no-op and failure publish no revision.

Preparation, current-state consequences, history append and retirement produce one candidate under the existing complete-save authority. Existing `PrepareAndPersist` and `ExactCompleteSaveAtomicPersistence` perform bounded candidate validation, eligible existing vacancy recovery, exact atomic replacement, durable readback validation and only then session/runtime publication. No sidecar, settlement journal, alternate writer or timestamp-based orphan promotion exists. Rollback uncertainty retains the established recovery-required contract; unchanged disk bytes are claimed only after proven rollback.

## History, storage and compatibility

Admission already allocated the identity. Settlement appends that RunId through bounded oldest-first history semantics using the current configured history bound and changes `NextRunSequence` **zero** times. Manual completion and B2 admission retain their respective one-increment paths. Latest is the newly appended final recent record, even when completion order differs from admission order.

`DurableSettlementHistory` is a narrowly constructed, exact-predecessor/retired-owner/expected-history authorization. Player builds expose no factory. Generic active history mutation validation and manual allocator checks remain in force. The settlement merge copies original retained outcome JSON nodes, history extensions, compatible explicit nulls and lexical extension values rather than round-tripping those through Unity DTOs. Conflicting/duplicate visible identities fail complete-save/allocator validation before consumption.

Schema remains **15**; member order, frozen readers/migrations, unknown-member limits and parser budgets remain unchanged. B1 format **1** and `run.executable.living-dungeon-b1.v1` remain unchanged. C0/C2 execution is not checkpoint-enabled. Retirement releases byte/replay obligations through existing retained-record limits; no writable capacity counter is added.

## Committed work versus lookahead

`RunExecution.Prepare` (`RunExecution.cs:162`) returns immediately when `pending` exists. `NextDueTime` calls it, then calculates a timestamp without advancing the authoritative boundary. `ResolveCombatRoom` (`RunSimulationService.CombatC0.cs:16`, `:39`) performs planning/geometry/collection before yielding the announcement at `:41`. Collection changes derived positions in a private result, and charges bounded computational work; it does not resolve damage, publish receipts or mutate the kernel's monster/member condition. `kernel.Resolve` follows the announcement, at `:43`.

`AdvanceCore` (`RunExecution.cs:184`) checks the deadline before resuming the iterator. Successful commits stamp the ordinal, record receipts, and then set `CommittedCombatWork` and fold evidence (`:206`). An insufficient deadline leaves the pending event cached. `CombatCheckpointCodec.Inspection` (`CombatCheckpointCodec.cs:23`) records committed work; `Fold` also binds ordered combat receipts and resulting condition. `Export` does not call `Prepare` or `NextDueTime`. Therefore probing/exporting cannot insert pending work into committed evidence.

Restore creates a new kernel, with the same initial/route-planning charges, then advances exactly the committed ordinal (`CombatCheckpointCodec.cs:98`). The supplied work value is compared against deterministic reconstruction; it is never assigned to the kernel's counter. Replay does not prepare an additional event after its last commit. The next probe regenerates pending geometry once in that new execution, on top of the reconstructed committed work. Further probes in the same handle use its cached announcement.

Repeated restores do repeat bounded CPU work across calls. They neither sum those discarded computations into a surviving run nor erase committed charges. This is a per-execution workload guarantee, not a lifetime CPU quota across arbitrary repeated API calls. Parsing, hashing and validation remain bounded separately by checkpoint bytes/records/replay limits.

## Exact limits and failure

`CombatC0Kernel.ChargeGeometry` (`CombatC0Kernel.cs:43`) permits equality and rejects `units > MaximumWork - workCount` before incrementing. `ResolveStaged` (`:159`) stages additional work, HP and receipts, rejecting work above the same limit. It publishes counters/HP only after successful resolution (`:231`). Kernel initialization and event-bound planning remain charged exactly as in manual combat (`RunSimulationService.Execution.cs:89`, `:121`); this review does not redefine those charges.

Failure during lookahead or advancement marks the execution failed and disposes its iterator (`RunExecution.cs:159`, `:213`). It cannot subsequently export, advance, inspect a due time or take an outcome. A checkpoint made before that failed probe remains a valid committed prefix. Restoring that prefix need not reject a future failure: probing/advancing its next boundary deterministically fails again. B2 additionally probes `NextDueTime` during owner validation (`LivingDungeonContracts.cs:242`), catches the failure through `Validate`, rejects the owner and abandons the detached execution in `finally`. A malformed checkpoint or replay that itself exceeds its budget returns a null execution (`CombatCheckpointCodec.cs:113`). None of these paths invokes canonical settlement/publication.

## Captured input bounds

Floor count is checked against remaining bytes before allocating (`ActiveFloorRunSnapshot.cs:136`). Profile/priority counts also fit remaining bytes; geometry/continuity counts additionally fit captured work (`CombatStartCapture.cs:52`). Thus an untrusted integer cannot directly request an integer-sized allocation independent of retained bytes. The subsequent count-sized arrays have bounded technical overhead; the work ceiling is not an allocation-byte accounting unit.

Captured combat work must be positive and within the independent caller envelope before profile/geometry reconstruction (`CombatStartCapture.cs:80`). The supported profile sets, attack/range fields, geometry dimensions/tiles/connections and C2 identity/option/HP/revival state are validated before starting execution. Party generation uses the existing PhaseFiveB validation (3–5 members) before allocating member arrays. Geometry queues/path arrays depend on retained cells/path distances, not a numeric gross rectangle or attack range. Searches and line-of-sight loops charge the existing work owner. Configuration maximum rounds cannot bypass charged actor/target loops. These bounds apply under the injected qualification envelopes; this is not a new arbitrary-input performance benchmark.

Malformed/contradictory captures are rejected by the retained shared validation plus exact canonical recapture and replay evidence. No frozen B1 reader or migration is changed.

## Added qualification

`LivingDungeonB3B1Tests.cs:354` derives three work counts from an unchanged kernel execution of the existing canonical fixture: immediately after expensive encounter lookahead, immediately after that encounter commits, and at terminal outcome. For C0/C2 and one/two floors, it sets a test-only ceiling to each measured count minus one, equal, and plus one: 36 ceiling scenarios. Each compares uninterrupted advancement against four export/restore cycles per event, five repeated due-time reads per cycle, insufficient deadlines and eventual boundary commits. Assertions include exact steps, full structured outcomes, action receipts, monster/member condition, committed work and actual charged work. Failed boundaries must leave the committed prefix/condition/receipts unchanged and disable the failed handle.

Additional cases request replay beyond a smaller captured work ceiling, reject integer-maximum floor/profile counts before allocation, and verify B2 owner rejection when the next lookahead exceeds remaining work. Canonical session bytes and structured runtime/owner state are checked for publication side effects. These are new boundary qualifications; there is no before/after runtime correction claim.

At the pending threshold, lookahead fits but encounter resolution still cannot fit; no encounter consequence commits. These deliberately tight, code-derived test ceilings qualify exhaustion semantics without changing the existing 1,000,000-work caller envelope or inventing production tuning. They are not a maximum-content stress or cross-device throughput benchmark.

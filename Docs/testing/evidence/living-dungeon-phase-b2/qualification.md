## Scale and performance limits

Both scale models use the actual B1 compatibility-route engine, immutable captured content, one spatial room per tagged synthetic floor, and test-only health allowing a longer route. They do not create canonical 25/100-floor dungeon snapshots or change production floor configuration. IDs, deterministic ordering, bounded 257-action batches, selected-floor independence and exact owner serialization/restart equivalence are tested. Timings include authoritative replay and full validation; validation is not suppressed.

| Synthetic route model | Parties | Maximum checkpoint | Initial aggregate binary bytes | Scheduled actions including closure | Uninterrupted scheduling | Split batches with restoration |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 25 tagged floors | 20 | 69,158 | 1,382,280 | 8,021 | 13,060.06 ms | 50,402.50 ms |
| 100 tagged floors | 5 | 225,904 | 1,129,326 | 8,006 | 40,716.53 ms | 72,459.56 ms |

These measurements are from the final safeguard full EditMode report. The actual terminal owner sizes are **1,849,511 / 1,508,348 bytes**, with **8,020 / 8,005** committed replay events respectively. Add the canonical base save for complete-save storage. A serialized checkpoint of binary length `n` needs `4*ceil(n/3) + 3*ceil(n/3072) + 1` bytes for the chunk array, plus party metadata. Both exceed Profile A's 64 KiB checkpoint and 640 KiB complete-save limits. The 25-floor model already exceeds the per-party limit by 3,622 bytes; the 100-floor model exceeds it by 160,368 bytes. Neither scenario qualifies complete-save persistence at production limits. The current canonical floor/executable qualification supports at most five floors (production profile two); the synthetic route is not a substitute for larger retained canonical geometry. The compatibility-route API has no selected-floor input; complete-save tests separately preserve snapshot inputs across closed-boundary player edits. No presentation selection participates in the scheduler.

At Profile A's retained-record limit, four records/two active produce 218,487 complete-save bytes, 155,923 aggregate checkpoint bytes and 50 committed replay events. Final safeguard EditMode: mean validation **29.90 ms**, reopen **122.72 ms**, complete transaction **194.36 ms**. Windows real-file unfinished-prefix reopening: **61,746 durable bytes / 41.53 ms**. Report archives retain other measurements; host variance is expected.

Independent boundaries: exact **65,536-byte**, zero-event checkpoint restoration took **5.54 ms**; exact **2,048-event** restoration took **69.60 ms** with a **284,562-byte** synthetic checkpoint and a larger injected byte budget. That replay fixture cannot fit Profile A. A padded dormant **655,360-byte** complete save validated in **90.26 ms** and reopened in **90.78 ms**; 655,361 bytes rejected. This last measurement qualifies the complete-save parser/round-trip ceiling only, not active admission or ordinary writes of such large unknown extensions. The frozen-schema-13 source at exactly 262,144 bytes migrates to 262,223 bytes without changing predecessor bytes.

Mono's `GC.GetAllocatedBytesForCurrentThread()` returns zero on this host and is unavailable as trustworthy isolated allocation evidence. Unity's actual frame GC profiler in final PlayMode observed a **15,098,307-byte** maximum across five validation frames at four retained/two active; this includes Editor and test-harness allocations. It is not a precise isolated validator allocation measurement or a mobile result. The complete-save byte ceiling, checkpoint byte ceiling and replay ceiling are measured separately with explicitly synthetic inputs; no claim is made that all maxima are attainable together under Profile A.

Required follow-up dependencies: approved floor-capacity and attraction/suitability mapping; expanded floor/content/executable qualification; reviewed larger storage/parser profile and acceptable replay/reopen cost; terminal settlement/retirement; production clock mapping and offline attribution. Current results do not justify compression, snapshot deduplication, a journal or a second simulator. Any such change requires separate owner architecture approval. Production 20-party/100-floor readiness, balance, mobile performance and player-visible behavior are not established.

## Proposed durable representation

- **Openings.** Prefer explicit owner-scoped point IDs on structural endpoints of the edge, referencing the selected room/fixed definition. Extend the existing room connection-point table with reviewed eligible points and retain the `east`, `north`, `south` and `west` offsets and meanings. The optional dead-end cap has no point ID. One room-local cell and outward face per point, with canonical orientation/anchor transformation, keep choices and used doors unambiguous. Validate authored point uniqueness, boundary, reserved tiles, sockets and usable passage, then enforce room degree and one incident edge per occupied opening on the candidate. Coordinate-and-face persistence is an alternative but still needs authored-eligibility lookup and frozen transforms. Reusing the point records avoids introducing coordinate-based identity or translating persistent IDs when a room rotates. Do not move an existing authored point under its original ID.
- **Path and walls.** Prefer one edge-owned source-to-destination tile sequence for physical edges. Direct edges have only doorway attachments. Derive the `ResolvedTileFootprint` occupancy view in sorted order and derive walls from consecutive pairs plus validated doorway joins. Sorting the occupancy view never reorders the passage. A direction sequence or bend vertices could encode the same information more compactly, but expands normalization and parser failure modes for at most six cells. An additive format that also writes sorted occupancy would reduce some reader changes, but would require strict equality to derived occupancy on every read/write and one mutation authority. Prefer one durable path field for new-format edges and keep historical sorted footprints in frozen contracts. Side contacts leave closed boundaries even when several walking paths exist in the occupied tile set. One path index orders each reached interaction. Strict endpoint, length, axis, bounds, uniqueness, cardinal adjacency, no-overlap and graph validation prevent ambiguous traversal.
- **Content discriminator.** Prefer appending a distinct orthogonal category in [`SpatialContentContracts`][catalog], keeping `Straight = 1` and its whole-line orientation meaning. For the orthogonal category, `AllowedOrientations` explicitly lists permitted undirected step axes, including the doorway joins. Keep `Zero` for the vertical axis and `Ninety` for the horizontal axis. A compatible one-tile passage can turn at its only tile. An explicit versioned geometry field could preserve the category value on the current catalog record, but would add a second discriminator alongside the existing straight-oriented checks. Update the initial corridor's category under its stable definition ID, its maximum to 6, and validate zero monsters for the new category. Review the category-specific checks in [`SpatialContentValidation`][catalog-validator], the source schema and [`DungeonSpatialAuthoringPackage`][authoring], and the straight assumptions of construction, movement, deletion and optional-branch services. A retained legacy operation must preserve geometry and identities or fail with a localized blocker. Publish via the existing [export][export] and [build gate][buildgate]. Check exact source/export, parser registration, record budgets and compatibility-profile inputs.
- **Canonical bytes.** [`CanonicalSpatialSaveSerializer`][serializer] has an exact field list and no slot for selected doors or ordered corridor data on today's edge. [`CanonicalSpatialSaveContracts`][save-contracts] sorts and validates the legacy footprint as a coordinate-ordered collection. A tile set alone cannot disambiguate side-contact paths and a direct edge currently has no footprint. Encoding a new meaning into an existing ID, footprint order or ignored extension fails this contract. The preferred shape therefore requires an explicit versioned spatial/save registration decision in [`CanonicalSaveSchemaVersions`][versions] and exact round-trip handling through [complete save validation][full-save] and the [load coordinator][load]. Do not assign a schema number in PR 1. Review count limits, strict shape checks, frozen contracts, version refusal and [native creation][native] together. If the older development shape is refused under the [November 19 policy](pre-release-development-save-policy-2026-11-19.md), preserve originals and evidence, report the refusal, and use a separate native save or approved explicit reset. Schema 18 already uses native creation and has no 17→18 migration. Any migration later offered must be explicit and tested. A new build must retain exact current-schema readback, atomic and fail-closed [H1 recovery][h1], supported old executable behavior and R1 Research timing.
- **Durable draft intent.** A room placement command can carry floor/definition/anchor/orientation and deterministic identity binding. One accepted insertion command can bind the selected predecessor edge and new room and record both exact links, opening IDs and ordered paths. Gesture frames and unconfirmed suggestions need no command. Include path order and openings in canonical baseline/final fingerprints and in the versioned accepted command bytes. Format 5 hashes the authored catalog, manifest, compatibility and other rule inputs, but its existing vocabulary has no payload for these edits. If journal shape, command semantics or hashed rule framing changes, use an explicit new format or existing format/version mechanism as applicable. Keep older readers and recovery interpretation frozen. Rebuild against the proven baseline, rule identity and predecessor-complete committed prefix. Do not infer a confirmation from candidate bytes or silently re-suggest a path on replay. Pending, failed or unknown persistence blocks Save Changes. The draft candidate can represent incomplete connectivity without being admitted as current save state. At Save Changes, validate the exact acknowledged or recovered geometry and price the current canonical-to-final delta once. Failure preserves the draft and applicable recovery evidence.
- **Run inputs and replay.** Capture the actual connection from doorway to doorway, or to the optional cap. Movement consumes each captured step in order. Branch travel and assignment order use path indices, with existing sequence/ID ties, stop conditions and reverse return without repeat effects. Replace the Manhattan-derived terminal tile in [`PhaseFiveSaveContracts`][branch-save]. [Floor knowledge][floor-knowledge] and branch applicability must distinguish a changed opening or passage even if occupancy is identical. Old parties, their checkpoints and recorded steps keep their captured layout, geometry and executable rules. Qualify exact resume and settlement before extending any supported saved run contract. UI and replay consume captured motion or existing recorded steps. Never reconstruct historical detailed replay from the current map when evidence is unavailable. Use the existing read-only failure or coarse history path. No distance-based Heat, loot, damage, fatigue, danger or corridor combat is added.

### Suggestions for the first playable slice

Enumerate eligible required edges and compatible openings in deterministic order. Use a bounded search over legal cardinal paths under the authored length/work limits. Rank validated, supported candidates by configured gross construction charge if the existing pricing authority can evaluate it consistently for all considered candidates, then logical travel length and stable ordinal edge/opening IDs and path coordinates. If exact comparable gross price is unavailable, use shortest legal passage with the same ties and describe it as a geometry suggestion. A bounded search can report no suggestion while leaving manual editing available. Preview and Save Changes evaluate the same geometry under the same validation rules and show any current configuration or resource blocker. Use no estimated credit or substitute wallet authority. DL-GAME-024's complete net-mana ranking awaits Amendment C.

## Production-backed qualification layouts

The authored [floor][floors], [room][rooms] and [fixed-structure][fixed] data give Floor 1 a 12 × 12 envelope and 60 structural capacity, Floor 2 a 14 × 14 envelope and 80 capacity, a Basic Room 4 × 4, Entrance Hall 3 × 2 and Completion Terminal 2 × 2. Three Basic Rooms and fixed structures use 58 tiles before corridors. Capacity alone proves no fit.

- **Floor 1 middle insertion.** Seed the existing `compat.layout.r2` geometry from the [compatibility profiles][profiles] with a current-native, isolated test fixture. All orientations are Zero. Use Entrance `(0,0)`, Basic A `(0,2)`, Basic B `(0,6)`, and Terminal `(1,10)` at 42 occupied tiles. Preserve both fixed structures and their attached edges. Place new Basic N at `(4,3)` at 58 draft tiles. Replace the proved zero-investment direct A → B. Join A's east face at world cell `(3,4)` to N's west face at `(4,4)` directly. Join N's north face `(5,6)` through `[(5,7), (4,7)]` to B's east face `(3,7)`. Final use is 60 and the route is Entrance → A → N → B → Terminal. This case requires the additional legal A east opening at local `(3,2)`. The data must authorize it in the implementation catalog. No capacity increase is needed.
- **Floor 2 six-tile and side-contact case.** Use the [existing Floor 2 shell profile][shell] and its established entitlement and lifecycle rules. All orientations are Zero. Seed or build a valid required route with A at `(2,5)`, B at `(6,5)`, and a zero-investment direct A east `(5,6)` → B west `(6,6)`. Entrance `route` joins A south `(3,5)` via `[(2,2), (3,2), (3,3), (3,4)]`. B north `(8,8)` joins Terminal `route` via `[(8,9), (9,9), (10,9), (11,9), (11,10), (11,11)]`. Baseline use is 52. Position N at `(0,9)`. For the same explicit A → B replacement, join A north `(4,8)` to N east `(3,10)` via `[(4,9), (5,9), (6,9), (6,10), (5,10), (4,10)]`. Join N east `(3,11)` to B north `(7,8)` via `[(4,11), (5,11), (6,11), (7,11), (7,10), (7,9)]`. Final use is 80. The first passage's first and last tiles share a closed boundary, and `(7,9)` and `(8,9)` belong to different corridors with a closed boundary. Tile `(5,9)` touches A at `(5,8)` outside the selected north opening and that wall stays closed. Shortening the first passage to `[(4,9), (4,10)]` is a separate legal manual choice at 76 tiles. Each costs the configured amount for its distinct new tiles. The extra opening choices in these fixtures require reviewed noncorner Standard Passage records.
- **Fresh-save progression gate.** The native Floor 1 `compat.layout.r1` has one Basic Room. Each fixed opening's only exterior tile is in that room. Inserting at either direct edge while retaining all footprints is impossible, even with six tiles and movable room doors. #268's first-room confirmation does not prove an eligible follow-on insertion. Use the isolated two-room fixture to qualify the editing loop, or an already entitled, constructed Floor 2. Before making any fresh-save progression claim, prove a normal supported path to the authorable layout. If that path needs a changed initial starter anchor/profile, obtain explicit owner approval for the initial placement and review native creation and compatibility. Do not move an already placed fixed structure implicitly or grant Architecture eligibility for the demonstration.
